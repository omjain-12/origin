# Best open-source starting points for your agentic AI assistant

Your project is more than a standard RAG chatbot. It is a personal AI assistant with workflow orchestration, persistent memory, retrieval, and tool execution.

The ideal existing project should already implement most of these components so that you can focus on improving the architecture rather than rebuilding the entire application.

Your target architecture looks like this:

1\. User Input + Conversation History

Current message, previous chats, user profile

2\. Query Understanding and Expansion

Resolve references, rewrite queries, identify intent

3\. Retrieval + Memory

Relevant document chunks, personal facts, chat history

4\. Agent Workflow / LLM

Reasoning, routing, planning, tool selection

Action tools

Calendar, tasks, reminders, scheduler, alarms

Learning layer

Extract, update, and persist useful memories

Conceptual architecture for your project, not a claim that any one repository implements every component.

I looked for existing projects that combine chatbot functionality, RAG, agent workflows, tools, and persistent memory, while also considering your preference for Java/Spring Boot.

## 4. My recommendation

Given that your priority is to reuse an existing project, rather than build everything from scratch, I would narrow your choice to two.

Option A — Start with ai-rag-agent

Choose this if minimizing development time is your main priority. It already combines most of the application-level features you described, including persistent memory, document retrieval, tasks, reminders, and calendar APIs. You can retain the existing frontend and progressively replace or refactor components.

Option B — Start with Jarvis AI Platform

Choose this if Java/Spring Boot is a firm requirement. Its documented separation of orchestration, memory, retrieval, and tools is closer to the architecture you want. Expect to implement and test more of the personal productivity functionality yourself.

One important distinction: your learning layer should not simply save every conversation into the vector database. It should identify durable facts, preferences, and relevant updates, then persist those selectively. Both conversation history and long-term user memory need separate treatment.

You do not need to invent a Java agent framework. The official Spring AI project already supports chat clients, persistent conversation memory, RAG, tool calling, and MCP integrations.&#x20;

Repository: [spring-projects/spring-ai](https://github.com/spring-projects/spring-ai)

I would organize your application as follows:

01

API and conversation manager

Authentication, session IDs, current message, recent chat history

02

Context and retrieval pipeline

Query rewriting, user-memory retrieval, document search, reranking

03

Agent orchestrator

Intent routing, planning, tool selection, execution and retry logic

04

Tool registry

Calendar, scheduler, reminders, alarms and task CRUD

05

Memory and learning service

Extract candidate memories, deduplicate, update, persist and retrieve

06

Storage and background jobs

PostgreSQL + pgvector, chat history, task tables, scheduled job execution

Suggested stack:

- Backend: Java 21+ and a compatible Spring Boot/Spring AI release. Check their version compatibility before choosing dependencies.
- Agent tools: Spring AI `@Tool` methods or MCP servers.
- Workflow: Start with an explicit state machine or graph; add multi-agent delegation only when necessary.
- RAG: PostgreSQL with pgvector, hybrid retrieval, and reranking where useful.
- Memory: Separate session history from long-term user facts.
- Scheduling: Persistent jobs using JobRunr or an equivalent scheduler; do not rely on in-memory timers for reminders that must survive restarts.
- Frontend: React, if you want a web-based chat and productivity dashboard.

## 6. What I would build on top of the chosen repository

Start by getting the existing application running without changing its architecture. Then implement the missing pieces in this order:

1. Memory-aware retrieval: combine current input, conversation history, and relevant long-term facts before retrieval.
2. Query expansion: generate a small number of targeted alternative queries and merge their results using deduplication and reranking.
3. Structured tool contracts: define typed input/output schemas for tasks, calendar events, reminders, alarms, and scheduling.
4. Reliable execution: validate arguments, check dates and time zones, persist actions, and return the actual result to the LLM.
5. Learning layer: extract candidate memories after each interaction, resolve conflicts with existing facts, and persist only useful updates.
6. Evaluation: test retrieval relevance, correct tool selection, action success, memory accuracy, and whether the assistant invents completed actions.

For real-world actions such as deleting an event or changing an alarm, add confirmation and authorization checks rather than letting the model execute arbitrary operations unchecked.

Final verdict: Start by inspecting [ai-rag-agent](https://github.com/nitintayal/ai-rag-agent) for the most complete application-level feature match, and [Jarvis AI Platform](https://github.com/sujankim/jarvis-ai-platform) for the Java-first architecture. Neither should be treated as a verified drop-in implementation of every requirement until its code, tests, dependencies, and license have been checked.
